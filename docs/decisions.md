# 技術決策紀錄

每條決策寫下：決定了什麼、為什麼、什麼情況下要重新檢討。

## D1 前端：Next.js + TypeScript，手機優先、PWA

- **理由：** 公開服務需要 SEO，家長常搜尋「XX公園 溜滑梯」，每個場地都要有可被索引的獨立頁面；PWA 可以加到主畫面，暫時不用做原生 App。
- **重新檢討：** 需要推播、背景定位，或 App Store 曝光時。
- **PWA 進度（2026-10-17）：** 已加上 manifest（`src/app/manifest.ts`）與主畫面圖示（`pnpm icons` 產生，淺底綠圖釘，短名稱「放電地圖」）。還沒有 service worker，沒有離線功能。

## D2 地圖：MapLibre GL + OpenFreeMap 向量圖磚

- **理由：** 不用付授權費，可以自訂樣式；原型已經驗證可行。
- **樣式：** 使用者可以在地圖右下角切換彩色或灰階（2026-10-14），記在 localStorage（`pm.map`），不放進網址。
  - 預設彩色，用 `liberty`。
  - 灰階用 `positron`，原本的預設就是它。
  - 備援的 OSM 點陣圖磚只有彩色，灰階時用 CSS `grayscale` 濾鏡轉灰。
- **備援：** OSM 官方點陣圖磚（tile.openstreetmap.org），OpenFreeMap 載入失敗或 7 秒沒載入時自動切換。
  原本用 CARTO，2026-10 發現 CARTO 圖磚需要 API key（每張都有浮水印），改用 OSM。
  只在備援時使用、流量很小，符合 [OSM 圖磚使用政策](https://operations.osmfoundation.org/policies/tiles/)：不預先下載、不大量抓取、版權標示連到 osm.org/copyright。原型仍是 CARTO，未更新。
- **重新檢討：** 流量變大，或備援被頻繁使用（OSM 政策不允許大量使用）時，改成自架圖磚（Protomaps PMTiles）。

## D3 後端：Supabase（Postgres + PostGIS + Auth + Storage + RLS）

- **理由：** 會員、照片、權限一次到位，MVP 開發速度快；PostGIS 處理距離查詢最成熟。
- **重新檢討：** 商業邏輯變複雜，或需要排程與佇列時，再拆出獨立的 API 服務。

## D4 篩選在前端完成（依出發點載入附近縣市）

- **作法：** 每個縣市一份場地資料（含屬性與停車，做快取），並附上該縣市的範圍（bbox）。前端依出發點載入「範圍與出發點距離 20 公里內」的所有縣市，再在前端篩選與計算距離。
  例：從新竹市東區出發，會同時載入新竹市與新竹縣。
- **距離不限時只看選定的縣市（2026-10-18）：** 選了縣市就是想看這個縣市；距離不限時連隔壁縣市的場地全部列出來反而混亂。把距離設成 1–20 公里時，才依上面的規則把附近縣市算進來（`citiesToShow()`）。
- **理由：** 新竹市只有幾百處場地，資料量約數百 KB，篩選反應即時，也不會把使用者定位傳到伺服器。
- **重新檢討：** 單一請求的場地超過約 3,000 處，或要做跨縣市查詢時，改用 PostGIS 查詢（`ST_DWithin` + KNN 排序）。

## D5 屬性儲存：逐列記錄（EAV）為主，另外彙整一份 JSONB 給查詢用

- **主資料：** `place_attributes(place_id, key, value, source_id, verified_at)`，可以逐項記錄來源與確認時間。
- **查詢用：** `places.attrs jsonb`（例：`{"slide":"y","toilet":"u"}`）加 GIN 索引，由 trigger 或匯入腳本同步；只能讀，不能直接寫。
- **理由：** 逐列記錄好維護、好追溯；JSONB 讓篩選不用一直 join。
- **重新檢討：** 同步造成資料不一致時。

## D6 屬性三態與「包含資料未知」

- **理由：** 種子資料一定不完整，用布林值會把「不知道」誤判成「沒有」，把場地錯誤篩掉。
- **介面：** 預設只顯示確定有的場地，並提示「另有 N 處資料未知」，讓使用者自己決定要不要放寬。

## D7 路線時間：先估算，按需才算實際路線

- **現在：** 直線距離 × 1.35 估算；實際路線直接連到 Google 地圖。
- **P5：** 用 Docker 自架 OSRM 計算開車和步行時間，只算篩選結果的前 20 名並快取；大眾運輸維持連到 Google 地圖。
- **重新檢討：** 需要即時路況，或要在站內顯示大眾運輸路線時，評估 Google Routes API 的費用。

## D8 使用者回報：提交建議 → 審核 → 合併

- **理由：** 公開資料的可信度比成長速度重要；直接開放編輯容易被亂改。
- **作法：** `edit_suggestions` 表 + 後台審核頁；採納後寫入 `place_attributes`，來源記為 `user`，並記錄審核者。

## D9 座標與地址來源：OSM / TGOS

- **理由：** Google 的條款不允許把 Places 資料存進自己的資料庫。
- **狀態：** 已完成。72 處座標全部來自 OpenStreetMap（Overpass API，2026-10-10），比對結果在 `data/raw/osm-matches.tsv`。
- **授權：** OSM 資料採 ODbL，地圖與資料頁必須標示「© OpenStreetMap contributors」。

## D10 登入方式：Google、LINE、Email 登入連結

- **理由：** Google 最普及；LINE 是台灣家長最常用的帳號；Email 登入連結給不想綁社群帳號的人。
- **暫不做 Facebook：** 要通過 Meta 的應用程式審查，並提供刪除資料的回呼網址，前期維護成本高。
- **暫不做 Apple：** 做 iOS App 時再加（App Store 通常要求有第三方登入時也提供 Apple 登入）。
- **LINE 調查結果（2026-10-11）：**
  - Supabase Auth 在 2026-02 開放自訂 OAuth2／OIDC provider（[說明](https://supabase.com/docs/guides/auth/custom-oauth-providers)），但 **OIDC 模式不能用於 LINE 網頁登入**。
    - LINE 網頁登入的 ID token 用 HS256，以 channel secret 簽章（[LINE 文件](https://developers.line.biz/en/docs/line-login/verify-id-token/)）。
    - LINE 的 discovery 文件卻只列 ES256，JWKS 也只有 ES256 公開金鑰。
    - Supabase 用 go-oidc 依 JWKS 驗證，不接受 HMAC，所以一定驗證失敗。
  - **OAuth2（手動設定）模式**可能可行：只用 LINE 的 userinfo，不驗 ID token。
    - LINE 的 userinfo 沒有 email，要開 `email_optional`。
    - 文件沒寫是否支援本機 CLI，要用雲端專案與真的 LINE Login channel 實測。
  - **自己處理 LINE 流程**一定可行：伺服器跟 LINE 交換授權碼、用 LINE 的 verify API 驗證，再用 Supabase 管理 API 建立 session。缺點是網站伺服器要持有 service role key，登入流程也變成自己寫、要自己維護的安全敏感程式。
- **決定（2026-10-11）：**
  - P3(b) 先做 Google 與 Email 登入連結。
  - LINE 另外用 OAuth2 手動模式實驗：需要建立 LINE Login channel，用雲端 Supabase 測試。可行就加上，不可行再討論。
  - 不採用自己處理 LINE 流程。
- **決定（2026-10-17）：上線初期只開 Google 登入。**
  - 理由：網站唯一會寄的信是 Email 登入連結。Supabase 內建的寄信服務只適合測試，對外要另外設定 SMTP（自己網域的寄件信箱、SPF／DKIM，量大時要付費）。先不寄信，上線時就不用處理這些。
  - 作法：在正式環境的 Supabase 後台關掉 Email provider。網站讀 `/auth/v1/settings`（`authProviders()`）決定要不要顯示 Email 欄位，程式不寫死；本機與 CI 照樣開著，e2e 用 Mailpit 登入。
  - 影響：沒有 Google 帳號或不想用 Google 的人暫時不能登入（瀏覽、篩選不受影響）。服務條款寫「目前可以用 Google 帳號登入」。
  - 重新開放：有人反應需要時，先設定 SMTP（`docs/operations.md`），再打開 Email provider，並更新服務條款的用字。
- **Email 登入連結的作法：** 信裡的連結指向網站的 `/auth/confirm`，在伺服器端驗證 `token_hash`。換瀏覽器或裝置打開也能登入，不受 PKCE 必須同一個瀏覽器的限制。

## D11 使用者貢獻內容的授權（2026-10-11 決定：資料採 ODbL）

- **決定：** 使用者貢獻的資料（修正建議經審核採納的內容）採 **ODbL 1.0**。寫進服務條款（`/terms`），第一次提交前要勾選同意，並記錄同意時間（`profiles.terms_accepted_at`）。
- **照片：** 先不開放上傳（D17）。開放時再決定照片授權（候選：CC BY 4.0），並請使用者另外同意。
- **理由：**
  - 資料庫的座標全部來自 OpenStreetMap，本身就是 ODbL。整個資料庫採 ODbL，授權一致。
  - 保留開放資料、回饋 OSM 的可能。
  - 如果選 CC BY-SA，會跟 OSM 的 ODbL 不相容。
- **曾考慮的選項：**
  - A：資料 CC BY-SA 4.0、照片 CC BY 4.0
  - B：只授權網站非專屬使用
  - C：資料 ODbL、照片 CC BY 4.0（採用資料的部分）
- **影響：** 任何人（包括商業網站）都可以依 ODbL 使用資料：要標示出處，改作後的資料庫也要以 ODbL 公開。一旦有人貢獻，就很難回頭改授權。
- **待辦：** 上線前請法律顧問審閱 `/terms`、`/privacy`（目前標示「草稿，待法律審閱」）。

## D12 多縣市架構（2026-10 決定：先完成新竹市並上線，再依序拓展）

- **拓展順序：** 新竹市 → 新竹縣 → 桃園市 → 苗栗縣。新竹縣優先，因為與新竹市生活圈重疊（竹北、竹科），距離篩選跨縣市時最容易看出缺漏。
- **id：** `<縣市代碼>-<來源>-<編號或名稱>`，縣市代碼用三碼：`hsc` 新竹市、`hsq` 新竹縣、`tyc` 桃園市、`mlc` 苗栗縣（之後新增縣市沿用同一規則，代碼寫在 `cities` 表）。id 一旦公開就不改。
- **網址：** `/<縣市 slug>/places/<id>`，例如 `/hsinchu-city/places/hsc-luguang-park`；縣市首頁 `/<縣市 slug>`。slug：`hsinchu-city`、`hsinchu-county`、`taoyuan`、`miaoli`。
  直接開啟（或重新整理）場地網址時，畫面跟點選後一樣：地圖與清單，面板打開這個場地，地圖停在它上面；伺服器輸出的面板就有完整內容（SEO 不變），縣市的場地清單在瀏覽器載入，不內嵌在每一頁（2026-10-23）。
- **資料表：** 新增 `cities(code, slug, name, bbox, launched_at)`；`places.city` 改為參照 `cities.code`。尚未上線的縣市（`launched_at` 為 NULL）不出現在公開頁面。
- **匯入程式：** 每個資料來源一個轉接器（`scripts/sources/<來源>.py`），輸出統一的中間格式；比對、合併、座標替換、產生 review 清單共用同一套程式。`import_hccg.py` 在拓展前重構成第一個轉接器。
- **設施對照：** 各縣市的遊具用語不同（桃園寫「鞍式鞦韆」「高低單槓」，新竹寫「彈簧馬」），對照規則放在各轉接器裡，共用的同義詞放在共用表。
- **審核：** `moderator_cities` 已支援依縣市指派審核員。

## D13 清冊寫「無」遊具的公園不上地圖（2026-10 決定）

- **決定：** 選項 A。地圖只放有遊具的場地；清冊寫「無」的 23 處公園維持不匯入，列在 `data/review/hsc/no-playground.csv`。
- **理由：** 網站定位是「親子遊樂場」，結果都要是可以玩遊具的地方；無遊具的公園要另外設計顯示方式與篩選，也還沒有座標。
- **注意：** 有些大公園在清冊上寫「無」，遊具登記在別的名稱下（例：新竹公園的遊具在「新竹大砂坑公園」，已用別名合併）。
- **重新檢討：** 家長回報常常想找「草地跑跳、散步」的公園，或拓展到其他縣市時官方清單有完整的公園資料。

## D15 審核員與管理員不能直接寫場地資料表（2026-10 決定）

- **做法：** `places`、`place_attributes`、`place_parking`、`attribute_defs`、`sources` 對所有登入身分（包括審核員、管理員）都維持公開唯讀，沒有寫入的 RLS policy。
  - 使用者的建議只能透過 `review_suggestion()` 套用。
  - 審核員在後台編輯場地、還原修改紀錄，一律呼叫 SECURITY DEFINER 函式（P3(e) 實作）。函式負責：檢查 `can_moderate(city)`、強制寫入來源與確認日期、留下修改紀錄。
  - 匯入（`pnpm seed`）走資料庫直連，不經過 API。
- **理由：** 直接寫入可以繞過「每筆事實都要有來源」（CLAUDE.md 資料規則 3），例如寫入沒有 `source_id` 的屬性，或任意改來源。集中在函式裡，規則只要寫一次、測一次。
- **測試：** `tests/db/auth.test.ts`：匿名、會員、審核員、管理員直接寫入都失敗。
- **核准時修改後套用（2026-10-11，P3(e1)）：**
  - 基本資料（開放時間、地面材質）與封閉或維修的建議，審核員可以在核准畫面先修改內容，再由 `review_suggestion(…, p_payload)` 在同一個交易裡套用。
  - 修改後的內容一樣經過 `check_suggestion_payload()` 檢查。實際套用的內容存在 `edit_suggestions.applied_payload`，原始建議不變。
- **基本欄位的來源（P3(e1)）：** `places` 的開放時間、地面材質、狀態各有來源與確認日期欄位（`*_source`、`*_verified_at`），修改紀錄存在 `place_field_history`。
  - 封閉時記錄 `status_until`（預計恢復日期）與 `status_note`（原因）。
  - `reopen_place()` 恢復開放。
  - 重新匯入（`pnpm seed`）時，來源是 `user` 的值不被覆蓋，跟屬性的規則一樣。
- **還原與使用者管理（2026-10-11，P3(e2)）：** 一律透過函式。
  - 還原：`restore_attribute()`、`restore_field()`，回到某一筆修改「之前」的值、來源、確認日期，連匯入時的原始值也回得去。
  - 使用者管理：`admin_set_role()`、`admin_set_cities()`、`admin_ban()`、`admin_unban()`。
  - 管理員也不能直接寫 `profiles` 的角色與停權欄位、`moderator_cities`，所有角色變更都記在 `admin_log`。
  - 不能對自己的帳號操作，避免管理員把自己鎖在外面。
- **新增場地（2026-10-11，P3(c2)）：** `new_place` 的核准由 `review_suggestion()` 建立場地，審核員可以先修改名稱、地址、座標。
  - 新場地的 id 是 `<縣市>-user-<編號>`。
  - 停車一列（類型未知），屬性全是未知。

## D21 政府開放資料提供的座標可以使用（2026-10-13 決定，先用於臺北市）

- **遊具數量（臺北市）：**
  - 數量 > 0 → `y`。
  - 數量 0 → `u`，不當成「沒有」。組合遊具裡可能就有滑梯、鞦韆。

## D23 會員一起命名沒有名稱的遊戲場（2026-10-14 決定）

  - 只有管理員能在 `/admin/naming` 調整（`admin_set_naming_threshold()`），每次調整記在 `admin_log`，使用者管理頁看得到。

  - 已經有的票不受影響：未達新門檻的點留在待命名，等下一票或人工決定。門檻調低時不會自動補通過。
  - 通過時記下一致的人數（`resolved_votes`），匯出的確認者寫「會員 N 人一致」；之前通過的照當時的門檻寫「會員 3 人一致」。

## D25 拿掉「孩子年齡」與「場地規模」篩選（2026-10-17 決定）

- **理由：** 大部分場地的適用年齡是未知（`age_min`／`age_max` 為 null）。選了年齡後這些場地都會被濾掉（除非勾「包含資料未知」），實際上只是讓結果變少，對家長幫助不大。
- **只拿掉篩選：** 卡片的「年齡未知／3–12 歲」、場地頁的「適合年齡」、資料欄位、會員回報修正年齡都保留。資料齊全後要加回篩選很容易。
- **會員回報（2026-10-23 補上）：** 「回報修正 → 基本資料」可以回報「適合年齡」（兩個 0～18 的整數，最小 ≤ 最大，存成「3-12」）與「費用」（免費／收費），審核通過後寫入 `age_min`／`age_max`、`fee`，並記錄 `age_source`／`fee_source` 與確認日期；重新匯入時保留會員回報的值（migration 0034）。
- **場地規模也拿掉（同一天）：** 規模不是量測得來的。有清冊的縣市依清冊列出的遊具種類數推估（`scripts/sources/hccg.py` 的 `estimate()`：0–2 項小型、3–5 項中型、6 項以上大型），各縣市清冊寫法不同、無法比較，也不代表實際面積；只用 OSM 的縣市全部未知。場地頁的「規模」與 `size_class` 欄位保留。
- **舊的分享連結：** 網址的 `age`、`size` 參數直接忽略，連結照樣打得開，條件更新後網址就不再有 `age`。
- **原型：** 原型（`docs/prototype/playmap.html`）仍有年齡選單，網站不採用。`filter-cases.json` 移除 2 個只測年齡的案例與「小型場地」，「孩子 3 歲＋遮蔭＋5 公里」改成「遮蔭＋5 公里」，答案用 `pnpm regen:filter-cases` 從原型重新算（18 個案例）。原型仍有年齡與規模篩選。


## D26 遊樂設施類別＝其中任一種（2026-10-17 決定）

- **理由：** 家長多半是「孩子想爬」，不在乎是攀爬架還是攀爬牆；單項資料也不齊（全台攀爬架 93 處、攀爬牆 20 處），只篩一項會漏掉場地。直接把整類全勾沒有用：遊樂設施是 AND，全台 1,237 處裡每一類「全都有」都是 0 處。
- **語意：** 篩選面板的類別名稱（滑行擺盪、攀爬平衡、玩沙玩水、跑跳體能、感官創意）可以按，意思是「這一類有其中任一種」。類別內 OR：有一項 `y` 就通過；都不是 `y` 時，開啟「包含資料未知」且至少一項 `u` 才通過；全部 `n` 不通過。類別之間、類別與單項、類別與生活機能都是 AND。
- **互相取代：** 同一類的類別與單項不同時選。按類別會清掉同類已選的單項；再點同類的單項，類別取消、改成只選那一項。
- **網址：** `grp=climb`（代號在 `src/lib/play-groups.ts` 的 `GROUP_IDS`：ride、climb、sandwater、active、sense）。沒有代號的類別不能整類選取。
- **卡片標籤：** 選了類別時，列出這一類裡場地「有」的設施；一項都沒有（靠包含未知通過）時列出未知的項目。
- **原型與標準答案：** 原型同步加上類別按鈕與判斷，`filter-cases.json` 新增 4 個類別案例（共 22 個），原型與正式版結果一致，沒有偏差。

## D27 登入的使用者可以儲存篩選條件（2026-10-17 決定）

- **範圍：** 篩選面板最上面的「我的篩選」。登入的人可以把目前條件存起來，最多 5 組，按一下就套用（取代目前條件，網址跟著更新）。看資料、篩選本身仍然不用登入；沒登入時只顯示「登入後可以儲存篩選條件」和登入按鈕，登入後回到原畫面（條件在網址上，不會不見）。
- **名稱：** 預設是條件摘要（例如「沙坑＋廁所＋5 公里內」，超過 20 字截斷），可以改，最多 20 字。可以改名、刪除（頁面內確認）。
- **存滿：** 第 6 組擋下並提示「最多 5 組，請先刪掉一組」，不會自動刪掉舊的。目前條件已經存過時也不能重複存。
- **存什麼：** `saved_filters.query` 是分享網址的 query string（`filtersToQuery()`），讀回來用 `queryToFilters()` 解析，過期的參數自動丟掉。出發點本來就不在篩選條件裡，不會存任何位置。
- **權限在資料庫：** RLS 只允許本人讀、新增、改名稱、刪除；匿名完全不能存取；欄位權限只開放新增 `name`、`query` 與更新 `name`。上限由 BEFORE INSERT trigger 把關（同一個人上 advisory lock，同時送出也不會超過）。刪除帳號時 ON DELETE CASCADE 一起刪除。
- **停權的人也可以存：** 這是個人設定、不公開，不需要先同意服務條款。

## D28 Google 登入改用 Google Identity Services（2026-10-17 決定）

- **問題：** 原本的 Google 登入（`signInWithOAuth`）是網站 → Supabase → Google，Google 收到的回呼網址是 Supabase 的網域，同意畫面寫「繼續使用 <專案代碼>.supabase.co」，家長看不懂、也可能不放心。
- **做法：** 設定了 `GOOGLE_CLIENT_ID` 時，網站自己顯示 Google 官方的登入按鈕（Google Identity Services），Google 直接把 ID token 交給網站，伺服器用 `signInWithIdToken` 換成 Supabase 的 session（一樣是 httpOnly cookie）。Google 的畫面顯示網站自己的網域。
- **安全：** 每次顯示按鈕產生新的 nonce，雜湊交給 Google、原始值交給 Supabase，Supabase 驗證簽章、audience（後台 Google provider 的 Client ID）與 nonce，token 不能被拿去重放。token 不記錄。
- **沒設定時：** 維持經過 Supabase 轉址的流程（本機、CI、Docker 預設），兩種流程登入後是同一個帳號（同一個 Google provider）。
- **其他選擇：** Supabase 自訂網域（`auth.<網域>`，需要 Pro 方案加購）也能解決，但要付費、要先有網域；這個做法免費，換正式網域後一樣適用。
- **設定：** Google Cloud 的 OAuth 用戶端要加「已授權的 JavaScript 來源」（網站網址），見 `docs/operations.md`。

## D29 使用者可以撤回自己還沒審核的建議（2026-10-18 決定）

- **原因：** 送錯或想改內容的建議原本收不回來：審核員、管理員不能審核自己的建議，同一個項目已有待審建議時也不能再回報（0006）。
- **規則：** 只有本人、只有待審核（`pending`）的建議能撤回，透過資料庫函式 `withdraw_suggestion()`（SECURITY DEFINER）；不新增 UPDATE policy，審核仍然只能透過 `review_suggestion()`。停權的人也可以撤回自己的建議。
- **撤回後：** 狀態改成 `withdrawn`，保留紀錄，「我的貢獻」顯示「已撤回」；審核後台不再出現，`review_suggestion()` 也不接受；同一個項目可以重新回報。
- **介面：** 「我的貢獻」每筆審核中的建議旁有「撤回」；場地頁重複回報出現「你已經回報過，正在審核中」時，可以直接「撤回那一筆」後重新送出。都在頁面內確認，不用瀏覽器的 confirm。

## D30 網站流量統計用 Vercel Web Analytics（2026-10-20 決定）

- **原因：** 想知道有多少人在用、常看哪些頁面與縣市、從哪裡連進來、常用哪些篩選。網站已經放在 Vercel，Web Analytics 不使用 cookie，裝好就能在 Vercel 後台看。
- **只在 Vercel 上載入：** `process.env.VERCEL === '1'` 才放 `<Analytics />`（`src/components/analytics/SiteAnalytics.tsx`）。本機、Docker 與 e2e 沒有 `/_vercel/insights`，也不該把測試流量算進去。
- **網址參數：** 送出前用 `analyticsUrl()`（`src/lib/analytics.ts`）處理。首頁與縣市頁保留篩選參數（只有篩選條件，出發點本來就不在網址裡，D4）；其他頁面只送路徑，避免送出管理後台的搜尋字（可能是 Email）、登入頁的 `next` 等。
- **不送自訂事件：** 只有頁面瀏覽，所以不會有位置或帳號資料。隱私權政策「第三方服務」有列出。
- **要在 Vercel 專案的 Analytics 分頁啟用**才會收資料。

## D31 PostGIS 放在 extensions schema（2026-10-21 決定）

- **原因：** Supabase 安全檢查回報 `public.spatial_ref_sys` 沒有 RLS。這是 PostGIS 自帶的座標系統表，擁有者是 `supabase_admin`，我們不能開 RLS 也收不回權限；實測任何人都能用匿名金鑰透過 API 刪改。刪掉 SRID 4326，審核的距離判斷、新增場地、匯入都會壞掉。
- **做法：** migration 0033 把 PostGIS 移除後重裝在 `extensions`（不對 API 公開；PostGIS 不支援 `ALTER EXTENSION … SET SCHEMA`）。重裝前記下每一筆座標，重建 `geom` 欄位、索引與 `place_cards`、`naming_open` 兩個 view，逐筆比對座標，不同就整個退回。PostGIS 的函式也不再透過 API 公開。
- **之後的 migration：** 用到 PostGIS 的 SECURITY DEFINER 函式，`search_path` 要寫 `public, extensions`（DB 測試會檢查）；view 與 SQL 裡可以寫 `extensions.ST_*`。
