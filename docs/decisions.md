# 技術決策紀錄

每條決策寫下：決定了什麼、為什麼、什麼情況下要重新檢討。

## D1 前端：Next.js + TypeScript，手機優先、PWA

- **理由：** 公開服務需要 SEO，家長常搜尋「XX公園 溜滑梯」，每個場地都要有可被索引的獨立頁面；PWA 可以加到主畫面，暫時不用做原生 App。
- **重新檢討：** 需要推播、背景定位，或 App Store 曝光時。

## D2 地圖：MapLibre GL + OpenFreeMap 向量圖磚

- **理由：** 不用付授權費，可以自訂樣式；原型已經驗證可行。
- **備援：** OSM 官方點陣圖磚（tile.openstreetmap.org），OpenFreeMap 載入失敗或 7 秒沒載入時自動切換。
  原本用 CARTO，2026-10 發現 CARTO 圖磚需要 API key（每張都有浮水印），改用 OSM。
  只在備援時使用、流量很小，符合 [OSM 圖磚使用政策](https://operations.osmfoundation.org/policies/tiles/)：不預先下載、不大量抓取、版權標示連到 osm.org/copyright。原型仍是 CARTO，未更新。
- **重新檢討：** 流量變大，或備援被頻繁使用（OSM 政策不允許大量使用）時，改成自架圖磚（Protomaps PMTiles）。

## D3 後端：Supabase（Postgres + PostGIS + Auth + Storage + RLS）

- **理由：** 會員、照片、權限一次到位，MVP 開發速度快；PostGIS 處理距離查詢最成熟。
- **重新檢討：** 商業邏輯變複雜，或需要排程與佇列時，再拆出獨立的 API 服務。

## D4 篩選在前端完成（依出發點載入附近縣市）

- **作法：** 每個縣市一份場地資料（含屬性與停車，做快取），並附上該縣市的範圍（bbox）。前端依出發點載入「範圍與出發點距離 20 公里內」的所有縣市，再在前端篩選與計算距離。
  例：從新竹市東區出發，會同時載入新竹市與新竹縣。
- **理由：** 新竹市只有幾百處場地，資料量約數百 KB，篩選反應即時，也不會把使用者定位傳到伺服器。
- **重新檢討：** 單一請求的場地超過約 3,000 處，或要做跨縣市查詢時，改用 PostGIS 查詢（`ST_DWithin` + KNN 排序）。

## D5 屬性儲存：逐列記錄（EAV）為主，另外彙整一份 JSONB 給查詢用

- **主資料：** `place_attributes(place_id, key, value, source_id, verified_at)`，可以逐項記錄來源與確認時間。
- **查詢用：** `places.attrs jsonb`（例：`{"slide":"y","toilet":"u"}`）加 GIN 索引，由 trigger 或匯入腳本同步；只能讀，不能直接寫。
- **理由：** 逐列記錄好維護、好追溯；JSONB 讓篩選不用一直 join。
- **重新檢討：** 同步造成資料不一致時。

## D6 屬性三態與「包含資料未知」

- **理由：** 種子資料一定不完整，用布林值會把「不知道」誤判成「沒有」，把場地錯誤篩掉。
- **介面：** 預設只顯示確定有的場地，並提示「另有 N 處資料未知」，讓使用者自己決定要不要放寬。

## D7 路線時間：先估算，按需才算實際路線

- **現在：** 直線距離 × 1.35 估算；實際路線直接連到 Google 地圖。
- **P5：** 用 Docker 自架 OSRM 計算開車和步行時間，只算篩選結果的前 20 名並快取；大眾運輸維持連到 Google 地圖。
- **重新檢討：** 需要即時路況，或要在站內顯示大眾運輸路線時，評估 Google Routes API 的費用。

## D8 使用者回報：提交建議 → 審核 → 合併

- **理由：** 公開資料的可信度比成長速度重要；直接開放編輯容易被亂改。
- **作法：** `edit_suggestions` 表 + 後台審核頁；採納後寫入 `place_attributes`，來源記為 `user`，並記錄審核者。

## D9 座標與地址來源：OSM / TGOS

- **理由：** Google 的條款不允許把 Places 資料存進自己的資料庫。
- **狀態：** 已完成。72 處座標全部來自 OpenStreetMap（Overpass API，2026-10-10），比對結果在 `data/raw/osm-matches.tsv`。
- **授權：** OSM 資料採 ODbL，地圖與資料頁必須標示「© OpenStreetMap contributors」。

## D10 登入方式：Google、LINE、Email 登入連結

- **理由：** Google 最普及；LINE 是台灣家長最常用的帳號；Email 登入連結給不想綁社群帳號的人。
- **暫不做 Facebook：** 要通過 Meta 的應用程式審查，並提供刪除資料的回呼網址，前期維護成本高。
- **暫不做 Apple：** 做 iOS App 時再加（App Store 通常要求有第三方登入時也提供 Apple 登入）。
- **LINE 調查結果（2026-10-11）：**
  - Supabase Auth 在 2026-02 開放自訂 OAuth2／OIDC provider（[說明](https://supabase.com/docs/guides/auth/custom-oauth-providers)），但 **OIDC 模式不能用於 LINE 網頁登入**。
    - LINE 網頁登入的 ID token 用 HS256，以 channel secret 簽章（[LINE 文件](https://developers.line.biz/en/docs/line-login/verify-id-token/)）。
    - LINE 的 discovery 文件卻只列 ES256，JWKS 也只有 ES256 公開金鑰。
    - Supabase 用 go-oidc 依 JWKS 驗證，不接受 HMAC，所以一定驗證失敗。
  - **OAuth2（手動設定）模式**可能可行：只用 LINE 的 userinfo，不驗 ID token。
    - LINE 的 userinfo 沒有 email，要開 `email_optional`。
    - 文件沒寫是否支援本機 CLI，要用雲端專案與真的 LINE Login channel 實測。
  - **自己處理 LINE 流程**一定可行：伺服器跟 LINE 交換授權碼、用 LINE 的 verify API 驗證，再用 Supabase 管理 API 建立 session。缺點是網站伺服器要持有 service role key，登入流程也變成自己寫、要自己維護的安全敏感程式。
- **決定（2026-10-11）：**
  - P3(b) 先做 Google 與 Email 登入連結。
  - LINE 另外用 OAuth2 手動模式實驗：需要建立 LINE Login channel，用雲端 Supabase 測試。可行就加上，不可行再討論。
  - 不採用自己處理 LINE 流程。
- **Email 登入連結的作法：** 信裡的連結指向網站的 `/auth/confirm`，在伺服器端驗證 `token_hash`。換瀏覽器或裝置打開也能登入，不受 PKCE 必須同一個瀏覽器的限制。

## D11 使用者貢獻內容的授權（2026-10-11 決定：資料採 ODbL）

- **決定：** 使用者貢獻的資料（修正建議經審核採納的內容）採 **ODbL 1.0**。寫進服務條款（`/terms`），第一次提交前要勾選同意，並記錄同意時間（`profiles.terms_accepted_at`）。
- **照片：** 先不開放上傳（D17）。開放時再決定照片授權（候選：CC BY 4.0），並請使用者另外同意。
- **理由：**
  - 資料庫的座標全部來自 OpenStreetMap，本身就是 ODbL。整個資料庫採 ODbL，授權一致。
  - 保留開放資料、回饋 OSM 的可能。
  - 如果選 CC BY-SA，會跟 OSM 的 ODbL 不相容。
- **曾考慮的選項：**
  - A：資料 CC BY-SA 4.0、照片 CC BY 4.0
  - B：只授權網站非專屬使用
  - C：資料 ODbL、照片 CC BY 4.0（採用資料的部分）
- **影響：** 任何人（包括商業網站）都可以依 ODbL 使用資料：要標示出處，改作後的資料庫也要以 ODbL 公開。一旦有人貢獻，就很難回頭改授權。
- **待辦：** 上線前請法律顧問審閱 `/terms`、`/privacy`（目前標示「草稿，待法律審閱」）。

## D12 多縣市架構（2026-10 決定：先完成新竹市並上線，再依序拓展）

- **拓展順序：** 新竹市 → 新竹縣 → 桃園市 → 苗栗縣。新竹縣優先，因為與新竹市生活圈重疊（竹北、竹科），距離篩選跨縣市時最容易看出缺漏。
- **id：** `<縣市代碼>-<來源>-<編號或名稱>`，縣市代碼用三碼：`hsc` 新竹市、`hsq` 新竹縣、`tyc` 桃園市、`mlc` 苗栗縣（之後新增縣市沿用同一規則，代碼寫在 `cities` 表）。id 一旦公開就不改。
- **網址：** `/<縣市 slug>/places/<id>`，例如 `/hsinchu-city/places/hsc-luguang-park`；縣市首頁 `/<縣市 slug>`。slug：`hsinchu-city`、`hsinchu-county`、`taoyuan`、`miaoli`。
- **資料表：** 新增 `cities(code, slug, name, bbox, launched_at)`；`places.city` 改為參照 `cities.code`。尚未上線的縣市（`launched_at` 為 NULL）不出現在公開頁面。
- **匯入程式：** 每個資料來源一個轉接器（`scripts/sources/<來源>.py`），輸出統一的中間格式；比對、合併、座標替換、產生 review 清單共用同一套程式。`import_hccg.py` 在拓展前重構成第一個轉接器。
- **設施對照：** 各縣市的遊具用語不同（桃園寫「鞍式鞦韆」「高低單槓」，新竹寫「彈簧馬」），對照規則放在各轉接器裡，共用的同義詞放在共用表。
- **審核：** `moderator_cities` 已支援依縣市指派審核員。

## D13 清冊寫「無」遊具的公園不上地圖（2026-10 決定）

- **決定：** 選項 A。地圖只放有遊具的場地；清冊寫「無」的 23 處公園維持不匯入，列在 `data/review/hsc/no-playground.csv`。
- **理由：** 網站定位是「親子遊樂場」，結果都要是可以玩遊具的地方；無遊具的公園要另外設計顯示方式與篩選，也還沒有座標。
- **注意：** 有些大公園在清冊上寫「無」，遊具登記在別的名稱下（例：新竹公園的遊具在「新竹大砂坑公園」，已用別名合併）。
- **重新檢討：** 家長回報常常想找「草地跑跳、散步」的公園，或拓展到其他縣市時官方清單有完整的公園資料。

## D15 審核員與管理員不能直接寫場地資料表（2026-10 決定）

- **做法：** `places`、`place_attributes`、`place_parking`、`attribute_defs`、`sources` 對所有登入身分（包括審核員、管理員）都維持公開唯讀，沒有寫入的 RLS policy。
  - 使用者的建議只能透過 `review_suggestion()` 套用。
  - 審核員在後台編輯場地、還原修改紀錄，一律呼叫 SECURITY DEFINER 函式（P3(e) 實作）。函式負責：檢查 `can_moderate(city)`、強制寫入來源與確認日期、留下修改紀錄。
  - 匯入（`pnpm seed`）走資料庫直連，不經過 API。
- **理由：** 直接寫入可以繞過「每筆事實都要有來源」（CLAUDE.md 資料規則 3），例如寫入沒有 `source_id` 的屬性，或任意改來源。集中在函式裡，規則只要寫一次、測一次。
- **測試：** `tests/db/auth.test.ts`：匿名、會員、審核員、管理員直接寫入都失敗。
- **核准時修改後套用（2026-10-11，P3(e1)）：**
  - 基本資料（開放時間、地面材質）與封閉或維修的建議，審核員可以在核准畫面先修改內容，再由 `review_suggestion(…, p_payload)` 在同一個交易裡套用。
  - 修改後的內容一樣經過 `check_suggestion_payload()` 檢查。實際套用的內容存在 `edit_suggestions.applied_payload`，原始建議不變。
- **基本欄位的來源（P3(e1)）：** `places` 的開放時間、地面材質、狀態各有來源與確認日期欄位（`*_source`、`*_verified_at`），修改紀錄存在 `place_field_history`。
  - 封閉時記錄 `status_until`（預計恢復日期）與 `status_note`（原因）。
  - `reopen_place()` 恢復開放。
  - 重新匯入（`pnpm seed`）時，來源是 `user` 的值不被覆蓋，跟屬性的規則一樣。
- **還原與使用者管理（2026-10-11，P3(e2)）：** 一律透過函式。
  - 還原：`restore_attribute()`、`restore_field()`，回到某一筆修改「之前」的值、來源、確認日期，連匯入時的原始值也回得去。
  - 使用者管理：`admin_set_role()`、`admin_set_cities()`、`admin_ban()`、`admin_unban()`。
  - 管理員也不能直接寫 `profiles` 的角色與停權欄位、`moderator_cities`，所有角色變更都記在 `admin_log`。
  - 不能對自己的帳號操作，避免管理員把自己鎖在外面。
- **新增場地（2026-10-11，P3(c2)）：** `new_place` 的核准由 `review_suggestion()` 建立場地，審核員可以先修改名稱、地址、座標。
  - 新場地的 id 是 `<縣市>-user-<編號>`。
  - 停車一列（類型未知），屬性全是未知。
  - `places.created_from_suggestion` 記錄是由哪一筆建議建立的。`pnpm seed` 不把這些場地列為多出來的場地，`--prune` 也不刪。

## D16 預設暱稱用「家長＋4 位數」，不用社群帳號名稱（2026-10 決定）

- **做法：** 第一次登入時暱稱預設為「家長 1234」（隨機 4 位數），使用者可以在 `/me` 修改。
- **理由：** Google、LINE 的名稱常常是真名，直接當成公開暱稱，會在使用者不知情時公開真名（CLAUDE.md：對外只顯示暱稱）。
- **介面：** 第一次提交前提醒使用者可以修改暱稱（P3(c)）。

## D17 先不開放照片上傳（2026-10-11 決定）

- **做法：** P3 只做修正建議與審核。P3(d)（照片上傳）延後。
  - `photos` 資料表與權限已經在 P3(a) 建好、有測試，先不使用。
  - `/me` 的「我的照片」區塊先隱藏（`PHOTOS_ENABLED`）。
- **理由：** 照片是 P3 風險最高的部分：
  - 孩童臉孔
  - 照片裡的 GPS 等 EXIF 資訊
  - 別人的照片被冒用上傳
  - 審核員要逐張看
  - Storage 費用

  先讓修正建議的流程穩定。
- **之後開放時：**
  1. 補 Storage bucket、移除 EXIF 的處理、照片審核畫面
  2. 刪除帳號時清除照片檔案
  3. 決定照片授權（D11），並請使用者同意

## D18 管理員看得到使用者的 Email（2026-10-11 決定）

- **做法：**
  - 只有管理員能透過資料庫函式 `admin_list_users()` 讀取 Email（`auth.users`），並可以用 Email 搜尋。這個函式第一行就檢查 `is_admin()`。
  - 只出現在 `/admin/users`。審核員、會員、公開頁面與一般 API 都拿不到。
- **理由：** 家長來信要求協助（例如帳號問題、刪除資料）時，管理員要能找到對應的帳號；同名暱稱很多時，只靠暱稱無法辨識。
- **限制：**
  - 只用於處理帳號問題。

## D20 沒有官方清單的縣市：用 OpenStreetMap 遊戲場起步（2026-10-11 決定，用於新竹縣、苗栗縣、新北市、臺中市）

- **資料：** 只收 OSM 的 `leisure=playground`（`scripts/fetch_osm_city.py`）。
  - 用 Overpass 的 `is_in` 查每個遊戲場位在哪個有名稱的公園、哪個鄉鎮市（台灣的鄉鎮市是 `admin_level=8`）。
  - 結果存成 `data/raw/<縣市>/osm.json` 提交進 repo，匯入時不連網路。
- **名稱（不推測）：**
  1. 在有名稱的公園裡 → 公園名稱。同一個公園裡的遊戲場合併成一處，座標用 OSM id 最小的那個；各遊戲區自己的名稱寫在說明裡。
  2. 不在公園裡、但自己有名稱 → 自己的名稱。
  3. 都沒有 → 人工命名表 `data/raw/<縣市>/manual-names.tsv`（要填依據與確認者）。表裡也沒有的列在 `data/review/<縣市>/unnamed.csv`，**不上地圖**。
  4. 命名表寫「（排除）」的不上地圖，例如 OSM 標錯或私人社區。
- **屬性：** 遊具、生活機能全部是 `u`，停車類型未知；規模、停留時間、年齡、收費也是未知，**不估算**。遊具資料靠家長回報（P3）。
- **id：** `<縣市>-osm-<n|w|r><OSM id>`，例如 `hsq-osm-w974869027`（D12）。
- **上線：** 匯入不會上線。上線時間由人決定（`pnpm city launch`）。
- **有官方清單的縣市也可以用 OSM 遊戲場補充**（2026-10-12，先用於桃園市：官方資料只有特色公園）。
  - 官方場地優先。
  - OSM 遊戲場已經被官方場地涵蓋的，不另外建立場地。判斷依序如下，**不推測**（`sources/tycg.py` 的 `split_osm`）：
    1. 所在公園（或遊戲場本身）就是官方場地座標所用的 OSM 物件 → 涵蓋。
    2. 所在公園或遊戲場的名稱與官方場地相同，而且在 500 公尺內 → 涵蓋。同名但很遠的是別的公園，例如桃園有好幾個「中正公園」。
    3. 離官方場地 150 公尺內、名稱不同 → 列進 `osm-near-official.csv`，**不上地圖**，等人工在 `manual-names.tsv` 判斷：
       - 填「（排除）」＝同一處。
       - 填名稱＝不同處。
  - 涵蓋的列在 `osm-covered.csv`，方便抽查。
- **新竹縣的結果（2026-10-11）：**
  - OSM 遊戲場 83 個 → 場地 42 處，另有 14 處遊戲區合併進同一個公園。
  - 沒有名稱、也不在公園裡的有 27 個，等人工確認。
  - 行政區：竹北 47、芎林 12、竹東 7、湖口 6，其他零星（以遊戲場計）。

## D21 政府開放資料提供的座標可以使用（2026-10-13 決定，先用於臺北市）

- **背景：** 原本座標只能來自 OSM、TGOS 或實地測量。臺北市公園處的「臺北市公園設施資料」（136476）每處遊戲區都附座標，而且是遊戲區本身的位置，比 OSM 的公園中心點更準。
- **規則：**
  - 授權必須明確，例如政府資料開放授權條款第 1 版。來源、取得日期、原始座標系統都要記錄在 `data/raw/`。
  - TWD97 二度分帶（TM2）用 `scripts/lib/twd97.py` 轉成 WGS84，不加新套件。TWD97 與 WGS84 的差異在公分等級。
  - 轉換後不在縣市範圍內的不上地圖，列進 review。
  - **仍然禁止 Google**：任何來自 Google 地圖的座標、連結或內容都不能使用。
- **驗證（臺北市，2026-10-13）：** 415 處裡，314 處在 OSM 上有同名的公園或遊戲場。轉換後的座標跟它們的距離中位數 20 公尺、90% 在 76 公尺內，沒有超過 1 公里的。
- **遊具數量（臺北市）：**
  - 數量 > 0 → `y`。
  - 數量 0 → `u`，不當成「沒有」。組合遊具裡可能就有滑梯、鞦韆。
  - 組合遊具、擺盪船索、其他：不對照屬性，只寫進說明。擺盪船索比照桃園「擺盪大索不算鞦韆」的決定。

## D22 遊具用語：「圓盤鞦韆」就是鳥巢鞦韆（2026-10-13 決定）

- 「圓盤鞦韆」與「鳥巢鞦韆」是同一種遊具，對照到 `nest_swing`。
- 「鳥巢鞦韆也算盪鞦韆」的規則不變：也對到 `swing`，篩選「盪鞦韆」時一樣會出現。
- 規則在 `sources/hccg.py`、`sources/tycg.py` 的 RULES。臺北市的資料是數量欄位，沒有這個用語。
- 綠光公園原本同時列出網路文章的「圓盤鞦韆」與清冊的「鳥巢盪鞦韆1座」，其實是同一座，所以拿掉網路文章那一筆，改用清冊。
